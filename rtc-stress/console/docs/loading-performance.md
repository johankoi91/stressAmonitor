# 控制台加载优化 · 2026-11-24

问题主要在传输量及缓存策略。旧任务列表将所有历史任务的完整配置、进程、UID、机器快照和日志一次性返回；所有响应还被统一设置为 `no-store`，JS/CSS 和 JSON 均未压缩。旧 `/api/tasks` 在服务器本机约 30 ms，在此次公网采样中约 156 s、3,985,427 bytes。

## 修改

- `GET /api/tasks?summary=1` 返回历史列表摘要，保留原完整列表接口供旧调用方使用。
- 选中历史任务时才请求单条完整详情，缓存已读取记录，并合并并发请求；活跃任务仍持续更新。
- `GET /api/bootstrap` 一次返回设置、节点和音频元数据；取消紧随启动的重复节点/设置请求。
- 当前页面模块与初始数据并行加载。
- JSON/HTML 支持 gzip；构建时生成 JS/CSS 的 `.gz` 预压缩文件，静态下载不消耗运行时压缩 CPU。
- 带内容哈希的静态资源使用一年 immutable 缓存；HTML 使用 ETag 重新验证，API 数据继续 `no-store`。
- WebSocket 升级及音频/Range 传输绕过压缩，保留原始数据。

## 公网单次采样

下列为同一接口链路的观测，网络耗时会波动；任务列表前后载荷不同，完整详情现在单独读取。

| 请求 | 实际传输 | 解压后 | 耗时 |
|---|---:|---:|---:|
| 原完整任务列表 | 3,985,427 B | 同左 | 155.88 s |
| 新任务摘要 | 2,111 B | 9,066 B | 1.15 s |
| 单条完整详情 | 16,111 B | 194,446 B | 2.18 s |
| 合并初始数据 | 1,119 B | 2,697 B | 1.46 s |
| 主脚本首次获取 | 251,482 B | 788,261 B | 13.82 s |

主脚本原始传输约 787 kB、一次采样为 32.74 s。首次脚本更新仍受公网链路影响；资源缓存生效后无需重复下载，显式 ETag 重新验证返回 304。本次没有测量或承诺整个页面统一为 1.15 s；该数值是任务列表摘要请求。

## 验证

控制层 race 测试及 Go vet 通过，覆盖摘要字段、原接口兼容、gzip 与 q=0、预压缩文件、HTML/资源缓存、ETag 304、HEAD、Range 以及 WebSocket 升级。前端生产构建和预压缩通过。本地浏览器验证两条历史记录按需加载完整详情，无组件错误。

中心服务在确认无活跃任务后切换。A/B/C 均已重连在线；未启动媒体压测。内置浏览器的公网直连导航仍超时，公网传输观测使用 HTTP 实测；没有将该情况记为浏览器首屏通过。
