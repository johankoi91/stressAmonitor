## 当前分配

## CPU 原因与处理

### 采样结果

在 B 上使用 perf 的 cpu-clock:u，以 99 Hz 采样 10 秒，获得 9521 个样本，丢失 0。模块占比：RTC SDK 60.13%、AOSL 14.58%、libc 14.25%、vDSO 4.01%、pthread 2.75%，Go/helper 2.56%。

上述比例仅指所采进程的用户态样本，不含内核开销。同时用 /proc 读取各线程 CPU 增量并用 GDB 复核调用栈，热点在 aosl_main、SDK-IOQ、GENP 任务线程和 spdlog_pool。SDK 的内部符号已剥离，部分 perf 函数名会归到相邻导出符号，模块/线程归属比这些单个函数名可靠。

### 日志级别 0 被 C 初始化接口忽略

Go 配置默认 LogLevel 为 0，意图是 LOG_LEVEL_NONE。匹配版本的 agora_service_initialize 实际仅在 log_level 大于 0 时复制该字段，否则保持默认 INFO。读取该公开入口的反汇编确认了这个条件分支。

本地 Go SDK 适配在初始化成功后显式调用公开 API agora_service_set_log_filter(handle, 0)，使关闭常规日志真正生效。任务的结构化状态、音频计数、连接失败和 OnError 回调继续保留，实现使用 SDK 公开 API。

同样的 0/100/100 配额与合唱模式下，修复前 A 平均 CPU 约 28.0%，修复后约 21.5%；B/C 实时输入从约 69.5%/69.3% 提高至 76.0%/75.3%。该对照是校准运行，时长见结构化记录。

### 从合唱模式改为标准音频

此前一直使用超低延迟合唱场景。两频道、6 UID 的受控试验，PCM 格式、编码质量档位、素材和时序保持相同：

| 音频场景 | 实测 Opus 包时长 | 收到编码包 | 收到负载字节 | 活跃订阅 | 发送错误 |
|---|---:|---:|---:|---:|---:|
| chorus | 10 ms | 20959 | 1615918 | 8/8 | 0 |
| standard | 20 ms | 10470 | 1556416 | 8/8 | 0 |

收到的包数约减少一半，负载字节只减少约 3.7%，说明主要减少的是包数量及相应处理开销。标准模式减少了网络包处理、任务派发、锁和分配开销；最终 1000 UID 运行的每个 helper 都确认收到 20 ms 的 Opus 包。

这项优化将打包时长从 10 ms 增加为 20 ms，增加少量打包等待。控制台保留“超低延迟合唱”和“标准音频”两种选择，任务快照保存实际使用的模式。需要合唱延迟特征时应选择对应模式，并按其真实开销安排机器。

PCM 输入始终是 48 kHz、双声道、16 bit，SDK 编码质量始终是 AudioProfileDefault，保留全部 400 个发送 UID 的独立 PCM 编码路径。两种受控试验中 SDK 实际输出均为 Opus 单声道，这是默认编码档位的行为；PCM 输入声道数和编码输出声道数是两个不同指标。
